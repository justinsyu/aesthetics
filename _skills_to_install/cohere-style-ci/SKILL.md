# Cohere Style CI

## Core Contract

Create a fixed 16:9 HTML slide report and exported PDF using the tan Cohere-style CI format. Include only factual, evidence-backed information from primary sources published within the last 7 days inclusive of the current date.

If the user explicitly requests a broader market scan or vendor capability inventory, follow the requested time scope instead of the last-7-days default. These runs may produce evidence artifacts without a slide report, such as vendor evidence inventory JSON, website AI-capability screenshots with bounding boxes around supporting text, and a labeled screenshots PDF.

Never include recommendations, opinions, strategic advice, or unsupported interpretation. Every substantive statement in the output must have an inline citation hyperlinked to the source URL.

Viewer-facing report language must be scientific, objective, neutral in tone, and update-oriented. Avoid casual attribution such as "says"; use formal verbs such as "states," "reported," "listed," "describes," or "documented" as appropriate.

Use formal competitive-intelligence language in viewer-facing text. Avoid casual freshness framing such as "new" or "newly" when a precise source status is available; prefer terms such as "first-posted," "reported," "published," "during the reporting period," "the cited source set," or the exact source date. Avoid conversational explanation clauses such as "because the same sentence also covers..."; when scope qualification is required, state it formally as a source-scope limitation, such as "cited only for the subgroup explicitly named in the source."

Define unfamiliar accounting, pricing, policy, or industry terms in plain English near their first prominent viewer-facing use. Do not rely on technical source terms, such as "retained share," as standalone reader-facing language for general audiences; clearly distinguish spending shares, margins, receipts, and retained amounts from profit.

## Required Workflow

1. Create a run folder for every output, for example `competitive_intelligence_reports/<topic_slug>/<YYYY-MM-DD_HHMM>/`.
2. Inside the run folder, create:
   - `screenshots/date-verification/`
   - `screenshots/evidence/`
   - `screenshots/reference/`
   - `screenshots/render-review/`
   - `assets/`
   - `sources/`
   - `report.html`
   - `[disease]-ci-report-[MM.DD.YY].pdf`
   - `[disease]-ci-screenshots-[MM.DD.YY].pdf`
3. Copy `assets/tan_slide_background.png` from this skill into the run folder's `assets/` directory before building `report.html`.
4. Use the Codex Chrome plugin to open every webpage used as evidence. Load Chrome tools through the Chrome skill or tool discovery when needed. Screenshots must be from the actual open browser page, not from URL previews, search results, downloaded HTML, or non-browser renderers.
5. Verify each source publication date from visible webpage text in Chrome. Save a screenshot showing the visible publication date in `screenshots/date-verification/`, and ensure the exact date text has a visible highlight or bounding box in the saved screenshot. Do not rely on URL text, search snippets, page metadata, JSON-LD, file names, browser history, or LLM memory as the date source.
6. Define the requested topic, disease, population, product, geography, and evidence scope before extracting facts. Exclude adjacent or mixed-scope sources unless the in-scope subgroup, indication, result, or record is separately visible and cited.
7. Read primary sources directly before extracting facts. Do not identify or extract included facts from deterministic search outputs, snippets, secondary summaries, answer boxes, cached descriptions, or `web.run` results. Search may only help locate candidate pages; included facts must come from opened primary-source webpages or primary documents.
8. Before taking any webpage screenshot, close or accept all popups, modals, cookie banners, newsletter prompts, chat widgets, interstitials, sticky overlays, and other page chrome that obscures evidence or dates. Do not save screenshots while any such overlay remains visible.
9. Highlight or draw a bounding box around the exact supporting text on each webpage before capturing evidence screenshots. The highlighted or boxed supporting text must visibly appear in the saved screenshot itself, with enough surrounding context to validate the fact. Save these screenshots in `screenshots/evidence/`. If a page cannot show the relevant date and highlighted or boxed supporting text visibly, exclude that source.
10. Visually confirm each saved webpage screenshot before using it: the page must be unobscured, visible dates must be readable and marked with a highlight or bounding box, and evidence screenshots must clearly show highlighted or boxed supporting text. Retake any screenshot that fails this check.
11. Build the HTML deck using the style reference in `references/style-guide.md`, which tracks the current example report, and the copied background asset at `assets/tan_slide_background.png`. Open and follow the current example report before building or revising a deck. The current reference example is `examples/aml_reference_report/report.html`.
12. If sources or slides are removed during revision, renumber citations and any visible slide/page numbering, prune `report.html`, `sources/source-log.md`, `sources/reference-screenshots.csv`, and any numbered source extracts, and rebuild the screenshots PDF so final artifacts contain only cited references. Any remaining numbered support files such as `source-05-browser-text.txt`, `source-05-date.png`, and `source-05-evidence-01.png` must match the final report reference number; move excluded or superseded candidate materials into clearly labeled working/excluded paths instead of leaving them under final reference numbers.
13. Export the main report PDF with `scripts/export_html_slides_pdf.mjs` and name it `[disease]-ci-report-[MM.DD.YY].pdf`, where `[disease]` is the disease/topic slug and `[MM.DD.YY]` is the run date.
14. Export every date-verification and evidence screenshot used to support cited report references into one separate labeled screenshots PDF named `[disease]-ci-screenshots-[MM.DD.YY].pdf`. Each included screenshot page must show the reference/citation number(s) it supports, such as `Reference 3 - date verification` or `Reference 3 - evidence 1`.
15. Save the screenshot-PDF assembly manifest at `sources/reference-screenshots.csv` when using more than a few screenshots, with `label,path,caption` columns matching the labels in the screenshots PDF.
16. Review rendered screenshots of the exported main report PDF before finalizing. Fix any overlap, clipping, off-page content, excessive padding, table headers that wrap to more than one row, reference sections that spill beyond one page, or text below the minimum readable size.
17. Visually inspect the final labeled screenshots PDF before delivery. Confirm every included screenshot is readable, unobscured by overlays, correctly labeled, and visibly contains a highlight or bounding box around the source date or supporting evidence text.
18. Audit generated report and PDF hyperlinks for live resolution. Replace broken or dead source URLs with working canonical source URLs when available; otherwise remove the clickable annotation rather than leaving a broken link.
19. Validate the final report against the saved screenshots and the labeled screenshots PDF before delivery.

When revising an existing report and the user asks to follow the current instructions, re-apply the current workflow, language, style, evidence, export, and QA requirements to the revised artifact as a whole, not only to the explicitly changed copy or slide.

When creating year-over-year sibling artifacts from a prior validated report, preserve the validated layout patterns, link styling, citation styling, and export QA approach, but rebuild the data, evidence, source log, screenshots, citations, and reference artifacts from the requested year's current primary sources. Do not create the new artifact by retitling or date-shifting a prior report.

## Evidence Rules

- Use only information published in the last 7 days, counting the current date as day 0 and including both endpoints.
- For explicitly requested broader market scans or vendor inventories, use the user's requested time scope and document that scope in the source log or JSON output.
- Prefer primary sources: company press releases, SEC filings, regulator pages, clinical trial registry records, conference abstracts, journal articles, product labels, payer documents, and official organization pages.
- For healthcare-investor CI on private or portfolio-like companies, prioritize source-backed fields that inform investment judgment, such as clinical stage, modality, indication, differentiation, regulatory milestones, financing and ownership signals, partnerships, market access or reimbursement context, competitive set, and near-term catalysts; treat AI primarily as a collection or workflow aid unless the source-supported company thesis is specifically AI-centered.
- For early-stage healthcare-investor CI, include source-backed team, governance, execution, development strategy, portfolio or asset-management, and management-quality signals where available, such as leadership experience, board or investor involvement, operating history, clinical-development execution, asset stewardship, and disclosed governance or management changes. Do not infer execution quality, asset quality, or failure causes beyond what primary sources support.
- For CI outputs assessing product-label-consistent evidence or RWE/HEOR/value claims, distinguish FDA-approved label claims from supplementary label-consistent evidence; record indication, population, comparator, endpoint, evidence source, study design, limitations, and claim context (payer/HCEI, HCP, patient, or general promotional); do not imply broader safety/effectiveness, superiority, or off-label use without source support, and keep disclaimers or limitations visually proximate and prominent.
- For public drug pricing data, cite and link the current webpage that hosts or provides access to the most updated data, not a PDF, spreadsheet, or document download. If supplied links do not contain pricing data, search the source website and relevant official or public websites for the pricing-data page.
- When operational access to public drug pricing is needed, preserve both the stable host or navigation webpage and the exact current data file URL or interactive data endpoint in the source log, because current file URLs may change.
- For U.S. medication profit or dollar-flow infographics, define each dollar measure by source basis before visualizing flows: list price, net price, gross revenue, net revenue, rebate, discount, fee, margin, and profit are not interchangeable. Clearly state which stakeholder any profit pool applies to, and define net profit explicitly as source-supported profit after relevant costs rather than retained expenditures, gross profit, gross margin, or revenue. Do not label stakeholder receipts as profit or imply complete system-wide flows unless each channel, denominator, time period, and gross-to-net adjustment is source-supported and documented in the source log.
- When rebuilding drug-dollar-flow graphics from dated legacy estimates, do not present older estimates as current; prefer newer official data when available, such as ASPE 2020-2022 retained-share or intermediary-margin data, and keep older estimates only as clearly dated historical context with their source basis. Distinguish retained shares and margins from net profit.
- For public drug-dollar-flow or ASPE retained-share graphics, use plain-English measurement descriptions for general audiences. Explicitly define retained share as the portion of spending kept by a stakeholder after source-specified transfers or discounts, and intermediary margin as source-defined spread or compensation retained by non-manufacturer intermediaries. Name excluded channels, such as mail pharmacy or physician-administered/provider-office sales, when relevant; avoid phrases like "captured by manufacturer" unless the denominator and channel are clear.
- For public-policy stakeholder-impact infographics about most-favored-nation or international reference pricing, define the exact policy mechanism, legal or proposal status, geography, benchmark country set, price basis, affected drugs, affected payers or programs, and implementation timing before mapping impacts. Use plain-English labels for public-facing policy mechanics while preserving source-specific terms where needed for accuracy. Separate stakeholder groups such as patients, federal or state payers, manufacturers, providers, pharmacies, plans, employers, and non-U.S. health systems only when the cited source supports that group's exposure or effect; distinguish observed data, modeled estimates, statutory text, agency statements, and advocacy positions; and avoid causal access, savings, innovation, launch, or foreign-price claims unless the source explicitly supports the magnitude, direction, denominator, and time horizon.
- When building EU drug-pricing comparisons from downloaded files, preserve the raw source files, prefer extractable tabular formats over PDFs, and record interactive-only or non-pricing gaps in the source log. Do not compare prices across countries unless units, pack size, and price basis are normalized or the limitation is clearly caveated.
- For regulatory-approval, launch, and payer-policy timing infographics, record each date field with its source-specific meaning, such as FDA approval date, launch or availability date, policy effective date, policy revision date, posting date, or retrieval date. Do not calculate or imply coverage lag, payer reaction timing, or launch-to-policy intervals unless the compared date definitions are visible in primary sources and documented consistently in the source log or dataset notes.
- For cross-jurisdiction drug-launch infographics, keep FDA approval, EMA or European Commission authorization, and country-level European commercial availability or reimbursement as separate statuses. Do not label a product as launched in Europe unless a primary source visibly supports the exact European geography, launch or availability status, and date basis used.
- Before final export, independently re-audit CI data tables with approval, launch, or policy timing in row slices against primary sources and visual evidence screenshots; resolve any mismatch before delivery.
- For payer-policy or coverage-policy evidence, verify and preserve the visible first-publication, original-posting, effective, revision, and retrieval dates when those fields exist. When first-publication or original-posting dates support the timing claim, include appendix or screenshot-PDF proof pages with those date fields visibly highlighted or boxed.
- For vendor AI-capability inventories, collect direct vendor-website evidence into structured JSON with source URL, evidence text, screenshot path, and scope notes for each claim.
- For vendor AI screenshot appendices or capability inventories, perform an explicit-offering review pass before final inclusion. Retain only evidence that shows a vendor-offered AI product, service, feature, platform, workflow, or capability; exclude generic thought leadership, news, blog/sidebar-only mentions, search/category labels, and other AI references that do not document a specific vendor offering.
- Organize retained vendor AI evidence by company and canonical source URL, keeping all claims and screenshot paths for the same company-page pair together in the JSON, source log, manifest, or appendix structure.
- For vendor service-line or capability infographics across a product lifecycle, such as HEOR, market access, evidence generation, or commercialization services, retain only vendor pages that document offered services, capabilities, platforms, methods, deliverables, or named solution areas. Do not treat generic educational content, thought leadership, blog posts, or search/category labels as evidence of an offered service unless the page explicitly connects that content to a vendor offering. Map services to lifecycle stages only when the stage is explicitly stated by the source or when a transparent, source-logged taxonomy is applied consistently without implying vendor endorsement of that stage label.
- For HEOR-only lifecycle infographics, use HEOR vendor terminology and narrow project types to HEOR-performed work, such as evidence strategy, literature reviews, burden-of-illness, epidemiology, real-world evidence, outcomes research, economic modeling, patient-reported outcomes, and evidence dissemination. Exclude market access deliverables unless the user explicitly broadens scope, including payer tools, access execution, HTA submission management, pricing/reimbursement, AMCP/PIE/GVD communications, message testing, field training, launch sequencing, and LOE strategy.
- For vendor service-line lifecycle infographics, make visual encodings match the underlying taxonomy. Do not use numbered or color legends that imply mapping to lifecycle-stage columns unless those numbers or colors actually represent the stage columns. Place pre-launch RWE, burden-of-illness, epidemiology, landscape, and evidence-planning services before launch when the source or source-logged taxonomy supports that timing; do not imply that RWE work is only post-launch. Route connector lines so they do not cross labels, service names, citations, or stage headings.
- For large vendor/event competitive-intelligence sweeps, first extract the official roster from organizer or event sources; validate each vendor website domain with source/provenance before crawling or screenshotting it; and record limitations for uncrawlable, blocked, or unverifiable pages in the source log or working notes.
- For HCP or drug-website competitive-intelligence inventories, collect site-level records from rendered pages with canonical URL, brand name, generic name, company or labeler, exact reproducible hex palette values sampled from visible rendered UI elements, and real-world evidence status when requested. Treat RWE as present only when the page visibly documents real-world evidence, real-world data, registry, claims/EHR, postmarketing, observational, retrospective, or phase 4 evidence; record absent, uncertain, blocked, or not assessed explicitly rather than inferring from therapeutic class or prior knowledge.
- For manufacturer product-locator or provider-finder infographics, label records as public locator participants, listed providers, or participating practices unless the source explicitly states that the list is an authorized-retailer, authorized-account, certified-provider, or complete national master list. Preserve row-level CSV or JSON extracts separately from aggregate display data, record endpoint/radius/grid limitations in source notes, and avoid presenting partial, capped, blocked, or browser-origin extracts as exhaustive.
- For static GitHub Pages or browser-based provider-location maps built from scraped provider rows, keep the map data as a separate CSV or JSON artifact with stable row IDs, source URL or endpoint provenance, geocoding basis, scrape timestamp, and any deduplication or clustering rules. Make provider markers zoomable and clickable with row-level details tied back to the data artifact, include a non-map list or table fallback when feasible, and label the map as a visualization of the collected public locator records rather than complete provider coverage unless the source explicitly supports completeness.
- For provider-location dashboard or map toolbar metrics, stack a concise uppercase label such as `RECORDS SHOWN` above the numeric value, and align that label/value block with adjacent control labels such as `SEARCH` and `PRODUCTS`.
- For competitive-intelligence provider-location map toolbars, keep metric labels and control labels aligned in one label row, space toolbar groups evenly, and when product filters wrap, keep the first or highest-priority product in the first input-height row with secondary products in the row below. Align toolbar action buttons with the primary input/control row rather than the bottom of taller wrapped filter groups; avoid oversized leading gaps before search and preserve balanced spacing across metric, search, filters, and action columns. After controls are aligned, rebalance the toolbar's vertical padding so taller previous control layouts do not leave empty top or bottom space.
- For public provider-location dashboards, do not render empty map or chart surfaces while data is loading; show a concise loading or error state until the underlying locator data is ready.
- For provider-location map popups, verify every clickable row-level provider link by opening it from the rendered map or list before delivery. Use a provider-level URL only when it directly opens the specific provider, practice, or location record; if a manufacturer source locator URL opens only a generic search page, start page, or locator shell rather than the specific provider/location, keep that URL in source provenance and do not present it as the row-level provider link.
- For infographics based on site-level RWE signal terms, label visuals as observed site-language signals or term mentions, not validated clinical, regulatory, or promotional claims. Keep counts tied to assessed pages or records, include uncertain/blocked handling in notes, and avoid wording that implies the signal terms independently validate claim substantiation.
- When exporting RWE claim inventories to Markdown, use one row per assessed claim or page section with brand/generic/company fields, source URL, short evidence text or claim summary, RWE assessment label such as present, absent, uncertain, blocked, or not assessed, and any scope notes needed to explain the label.
- Do not treat general promotional-message extraction fields as RWE evidence claims. Promotional copy, efficacy messages, safety messages, access messages, convenience statements, mechanism statements, support-program copy, page headlines, and positioning language count as RWE only when the same visible text explicitly documents real-world evidence, real-world data, registry, claims/EHR, postmarketing, observational, retrospective, or phase 4 evidence.
- For HCP or drug-website promotional-message inventories, extract only short verbatim visible messages from rendered pages, preserving exact wording except for whitespace normalization. Store the source URL, brand/generic/company fields, message text, page location or selector when available, message type such as efficacy/safety/access/convenience/mechanism/support, selection rationale, and extraction status. Record blocked, no clear promotional message, or uncertain rows explicitly rather than filling gaps from labels, memory, or inferred positioning.
- For data-derived competitive-intelligence infographics built from a completed inventory CSV or JSON, treat the compiled dataset as the cited evidence layer: record the dataset path, row count, generation or modified timestamp, field definitions, and any excluded or blocked-row handling in the source log or notes. Aggregate color palettes into explicit, reproducible groups with visible hex values, counts, and clear binning rules; do not reopen or rescreenshot every source unless the infographic introduces new source claims beyond the compiled dataset.
- When user or reviewer feedback says data downloading should not be allowed, remove viewer-facing download buttons or links for JSON, CSV, source extracts, and source data files. Keep any required internal data loading, preserved raw files, source logs, or dataset notes available to the workflow without exposing them as user download affordances.
- For data-derived public-program infographics that use area-level socioeconomic measures, document each measure's source, vintage or release date, geographic unit, denominator, and join key in the source log or dataset notes. Label area measures as area-level context rather than individual participant attributes, keep program counts and socioeconomic measures on visibly distinct bases unless normalized, and place inline citations on every displayed program, geography, or socioeconomic claim.
- For quote or promotional-message audit infographics built from a completed CSV or JSON, synthesize coded themes, claim types, calls to action, source locations, and extraction statuses into reproducible counts or shares before selecting exemplar quotes. Preserve exemplar quote wording verbatim, keep each quote visibly tied to its brand/source record, separate no-quote, blocked, and uncertain rows from extracted-message denominators, and do not imply frequency beyond the coded dataset fields. When representative quotes appear in infographics, exact-source-verify each quote and provide source screenshots when requested.
- For evidence-backed conference, agenda, session-guide, or calendar-view decks, treat source completeness as part of the evidence standard. Use the official program, agenda, planner, or organizer pages where available; check relevant date, track, keyword, sponsor/company, abstract, and pagination/filter views before concluding that a session set is complete; and document the searched scope or exclusion basis in `sources/source-log.md` or working notes.
- For local conference-data archive apps or abstract-corpus dashboards, preserve source manifests, source URLs, download or generation timestamps, source-file hashes, record-level source links, data dictionaries, validation summaries, extracted tables or sections, and role-specific queues as separate audit artifacts. Label scoring, classifications, and role queues as triage aids rather than analyst-approved conclusions unless a human review step is explicitly documented.
- For interactive CI archive or dashboard pages that load local JSON, CSV, or generated datasets in the browser, include a concise visible loading state, replace placeholder metric text after successful load, and show a clear nontechnical error state if data loading fails. While data is loading, use the page's established loading style and do not render section headers, KPI cards, or empty chart containers until the corresponding data is ready. Do not leave permanent "Loading" labels, empty chart panels, or hidden failures in the delivered page.
- Exclude sources without a visibly verified publication date.
- Treat scope as part of the evidence standard. If a source covers a broader or adjacent topic than requested, include only facts that are explicitly about the requested scope; otherwise leave it out.
- For local venue, restaurant, or listing intelligence, treat Google Maps, popular-times, business-profile, and directory data as potentially partial, dynamic listing data unless the page itself provides a stable, cited source statement. Do not invent unavailable fields; label confidence or coverage limits in working notes or source logs; and distinguish listing/map observations from primary-source evidence such as venue websites, menus, filings, permit records, official announcements, or owner-published pages.
- For journal articles, abstracts, conference posters, white papers, or observational studies, treat study design details as evidence-bound scope facts: data-collection period, platform or data source, sample size, geography, population, and inclusion/exclusion criteria must be visible in the source and cited before they appear in the report.
- For ClinicalTrials.gov sources, do not treat `Last Update Posted` as sufficient evidence that the record contains a substantive update. Inspect the Record History and, when needed, compare record versions to identify what actually changed. Include a registry item only when the changed fields are substantively relevant to the report audience, such as medical affairs, market access, commercial, clinical development, regulatory, or similarly specified leadership readers. Exclude records whose recent activity is limited to administrative date updates, site/contact maintenance, or other low-substance changes.
- Treat all statements as claims requiring evidence. Use citations on the same sentence or clause as the supported claim.
- Use hyperlink citations such as `<a class="cite" href="https://example.com/source">1</a>`.
- When multiple inline citations appear together, separate them with commas so they render as `1,2,3`, not `123`.
- Ensure adjacent citation punctuation is part of the superscript citation run. Adjacent citations should render as superscript `3,4`, with no baseline comma or space between superscript numbers.
- Visible reference sections or slides in the main report must not show local file paths or local screenshot filenames. Use source names, visible publication dates, citation/reference numbers, and/or external source URLs only.
- Maintain a source log in `sources/source-log.md` with citation/reference number, source URL, visible publication date, screenshot path for date verification, screenshot path for each evidence screenshot, and facts extracted.
- When a candidate source is excluded for scope reasons, record the reason briefly in the source log or working notes so later revisions can distinguish "contains in-scope participants" from "supports an in-scope report fact." Keep excluded-candidate screenshots, browser-text extracts, and other working files clearly labeled as excluded or stored outside the final numbered reference sequence.
- Do not paraphrase beyond what the screenshot-supported evidence can substantiate.

## Report Language Rules

- State the report date range once on the first slide, using plain wording in the eyebrow chip or subtitle.
- First-slide report titles should follow the convention `[Disease] competitive intelligence update`, with the disease stated in title case and the phrase `competitive intelligence update` in lowercase unless the user explicitly requests a different title.
- Spell out the disease state in the report title unless doing so would force the title beyond two lines; only then use a clear abbreviation.
- When review feedback says the cover should only state the drug, product, company, disease, or other named subject, remove sponsor, context, deck-topic, report-type, and analysis-scope phrasing from the main cover title. Keep any necessary context in the subtitle, eyebrow, metric cards, metadata, or source log instead.
- When a cover title should include both a named product and topic or context, avoid phrasing that makes the sponsor or company name appear to be part of the product name. Prefer formats such as `[drug/product]: [topic/context]`, or move sponsor/company context into the subtitle, eyebrow, metric cards, or metadata.
- Define all abbreviations used in viewer-facing report or infographic text on first use, especially program, dataset, trial, endpoint, source, and measure abbreviations.
- First-slide subtitles should use the same content width as the title unless the layout is intentionally asymmetric for a user-provided design reference.
- First-slide structure should follow the current example report unless a user-provided design reference overrides it: title and date chip at top, metric cards directly under the title, then a dark `Executive summary` callout with substantive bullets and inline citations.
- First-slide elements must not repeat the same information across the subtitle, metric boxes, summary callouts, or other visible components. Give each element a distinct analytical role, such as scope/date framing, quantified activity, concrete findings, or implications directly supported by cited evidence.
- Title the first-slide summary block "Executive summary." Make it substantive enough to start a discussion by naming the concrete updates or findings, not merely stating that updates occurred.
- Clearly distinguish summary, explainer, and takeaway sections when more than one appears in the same artifact. Use summary sections for concise reported findings, explainer or methods sections for scope and measurement context, and takeaway sections for source-supported implications or synthesis; do not let labels, placement, or copy make these roles interchangeable.
- On the first slide, place "Executive summary" and the heading of any adjacent key callout in the same top row, with their supporting details, bullets, or evidence text below those headings rather than beside or above them.
- Viewer-facing executive-summary and metric-card subtext must use update-specific wording such as "this update" rather than generic production, audit, or deliverable language such as "the final report."
- Do not use an "Access note" label or imply a market-access issue when the cited update does not affect access, reimbursement, coverage, price, or availability. Use a neutral content-specific label instead, or omit the note.
- Do not use generic time-window labels such as "evidence window," "date window," "in the window," or "inside the window" anywhere in viewer-facing report text. When dates matter after the title slide, use concrete phrasing such as "between May 6, 2026 and May 12, 2026" or cite exact source dates.
- After the first slide, avoid non-actionable date wording in slide titles. Titles should communicate the substantive update, not merely that something happened during the report date range.
- Slide titles should state concrete source facts or update outcomes. Avoid weak connective verbs such as "highlighted" or "added" when they do not explain the actual update, and do not use compound titles that imply one source/action caused or highlighted an unrelated source fact.
- CI report slide titles, takeaway statements, callouts, and metric labels should be substantive and formal. Do not use process/source-mechanics constructions such as "[source type] sources reported," "[source type] sources did," or "[source type] sources said" unless the source artifact itself is the update being reported.
- Metric-card labels should describe the substantive activity being counted, such as disclosure type, development stage, meeting activity, access signal, or market signal. Avoid weak deliverable mechanics such as "sources cited" when a content-specific label is available.
- When slide titles contain two independent source facts or update outcomes, prefer separate sentences with periods over semicolons for readability, unless a semicolon is clearly required by the design or grammar.
- Viewer-facing slide titles, takeaway panels, and callout text must be source-content specific. Avoid vague labels such as "items" or "context"; name the concrete trial, program, source type, update, or finding supported by the cited evidence.
- When a trial, program, source, or other entity is first mentioned in viewer-facing text, include enough cited factual context for a leader reader to understand what it is, such as phase, population or scope, intervention, platform, sponsor, or source owner when those details are visible in the cited source.
- Do not include source publication-date or date-display commentary in main body slides. The report date range belongs on the first slide, while source/date verification belongs in `sources/source-log.md`, reference tables, or the labeled screenshots PDF.
- Do not use process-oriented viewer-facing sections such as "Factual scope," "Source construction," or "evidence construction." These are audit details, not report content.
- Keep source construction, screenshot provenance, date-verification process, and audit details in `sources/source-log.md`, the labeled screenshots PDF, or appendix material unless the user explicitly asks to show methodology in the report.
- When methodology notes are appropriate for viewer-facing artifacts, place them inside available whitespace with concise wording, preserving slide fit, readable type, and existing visual hierarchy; do not add or expand a methodology area if it creates crowding, clipping, or smaller evidence text.
- Remove nonessential source-matrix, process-summary, methodology-summary, and audit-summary slides when they duplicate a final References slide or do not add substantive competitive-intelligence insight.
- Keep data-source limitations, confidence labels, missing-field caveats, and map/listing-data methodology out of viewer-facing slides unless the user explicitly asks for methodology or source-quality notes; preserve those details in `sources/source-log.md`, working notes, or appendix material instead.
- Do not create viewer-facing source/extraction process slides, file-audit slides, extraction-discrepancy slides, or local file inventory slides unless explicitly requested. Keep extraction discrepancies, dataset mechanics, and local file inventories in metadata, source logs, or working notes; use cover and summary space for substantive key insights supported by citations.
- Do not add arbitrary numeric scores, grades, or method ratings to viewer-facing report slides unless the user explicitly asks for a scored framework or the score comes directly from a cited source. Prefer concise factual labels or cited source facts over invented scoring systems.
- When the user or review feedback asks to remove visible source notes, process notes, methodology notes, or explanatory labels from a viewer-facing artifact, remove them from the visible design entirely. Preserve necessary support in citations, source logs, reference slides, appendix material, or screenshot PDFs instead.
- Do not add subtitles, body blurbs, or intro text that merely repeats the slide title. Omit them unless they add distinct analytical detail supported by cited evidence; when used, give enough explanatory context to clarify the scope, method, comparator, population, outcome, or why the update matters.
- Do not use redundant callout text that repeats metrics or section summaries already visible on the same slide. If a callout is used, it must add objectively stated findings with inline citations.
