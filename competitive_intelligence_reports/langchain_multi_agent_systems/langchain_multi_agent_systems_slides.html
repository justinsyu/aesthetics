Why they show up

Multi-agent systems respond to scale pressure

  • Too many tools or domains for one prompt.
  • Independent read/research work that can run in parallel.
  • Separate ownership across teams, data sources, or workflows.
  • Stateful staged behavior where specialist prompts should change.
  • Production need for traceability, evals, and durable control.

Selection heuristics

Do not start with a team of agents until one agent becomes the wrong abstraction

Use multi-agent patterns when context, tools, ownership, parallelism, or staged state are the scaling pressure.
  • Router/subagents: independent read-heavy tasks.
  • Handoffs/swarm: direct specialist conversations.
  • Skills: lightweight specialization and progressive disclosure.
  • Custom LangGraph: deterministic steps mixed with agentic nodes.
  • Avoid agent teams for tightly coupled writes without strong integration logic.

What mature teams measure

Evals are the operating system for agent improvement

  • Resolution quality, hallucination, contradiction, and policy compliance.
  • Token, cost, latency, and error rates by node, tool, and model.
  • Regression quality from golden datasets and sampled production traces.
  • Human feedback calibration for LLM-as-judge metrics.
  • Source URLs, confidence, and reasoning traces for auditability.

Build guidance

General guidance from the case set

  • Start single-agent; split only when there is real scaling pressure.
  • Define narrow jobs, tools, prompts, output contracts, and ownership.
  • Keep state, context, and handoffs explicit.
  • Parallelize independent reads; serialize risky writes.
  • Treat failures as eval data and prompts as production assets.
